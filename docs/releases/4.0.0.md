# TeleHop 4.0.0 implementation and verification

For the player-facing changes since 3.0.1, read the [changelog](../../CHANGELOG.md). For a server upgrade, start with the [migration guide](../migration.md), then check the [commands](../commands.md) and [permissions](../permissions.md) for the member and staff roles on your network.

## Installation and compatibility

Place `telehop-bukkit-4.0.0.jar` in the `plugins/` directory of every supported Bukkit-compatible game server. Place `telehop-velocity-4.0.0.jar` on every Velocity proxy. A standalone installation needs only the backend JAR and a database. Match plugin versions across a network before enabling configured travel commands. [Setup](../setup.md) · [Server and Java versions](../version-compatibility.md)

The six Maven modules retain their names. The backend module lives in `paper/` and produces the public Bukkit JAR. The filename identifies the shared server API. The plugin name and data directory remain `TeleHop`. The backend continues to own commands, menus, listeners and the player lifecycle. `paper.platform` selects the available teleport, chunk and messaging presentation APIs at startup. `paper-versions` owns the shared version contract and the 1.21 and 26.x world-identifier adapters. Their class files target Java 21, including the adapter compiled against the newer API on JDK 25. The proxy uses the shared API available in Velocity 3 and 4. Operators choose a deployment profile independently of platform detection. [Platform adapters](../platforms.md)

## Configuration and commands

The backend and proxy data folders each have a root `config.yml`. `SINGLE`, `MULTI` and `CUSTOM` select one profile. The backend keeps the database, twelve command groups, six translations and runtime storage outside that profile. The proxy keeps its database and Redis credentials in shared files. Both maintain a migration history and recovery copies. Server names, regions, world mappings, labels, aliases and destinations come from the installation. [Backend layout and settings](../configuration.md) · [Velocity layout and settings](../velocity.md)

The backend source, JAR and installed data folder use the same paths for editable templates. The root selector points to the local setup guide in `config/WIKI.md`. A fresh installation provides eight SINGLE settings files, ten MULTI files and ten CUSTOM files. Each instance generates its own storage and migration records. [Bundled setup guide](../../paper/src/main/resources/config/WIKI.md)

The grouped YAML supports additional spawn, hub and RTP labels. A variant has an identifier independent of its aliases. RTP variants use the common travel service, including its safety search, warmup and cooldown. The destination resolves its own definition before placing the traveller. Set a global warp permission or grant individual warp access. Menus, suggestions and direct commands apply the permission checks. [Command reference](../commands.md) · [RTP configuration and inheritance](../rtp.md) · [Warps](../warps.md)

Use `/telehop config validate` to check the candidate on disk, `/telehop platform info` to inspect the chosen adapter, `/telehop migration status` to inspect the migration and `/telehop diagnostics` for the deployment and database circuit. `/telehop reload config` and `/telehop reload messages` allow separate reloads. Changes to profile, connection settings or registered command labels require a restart. The permission reference lists each member and staff permission and each dynamic pattern, including `telehop.command.<id>` and the four RTP destination scopes. [Permissions and LuckPerms](../permissions.md)

## Routing and storage

Single-proxy transfers use the connection of the player who started the trip. On a network with several proxies, Velocity exchanges player presence and network operations through Redis. An accepted teleport request uses the accepting player's connection even when someone else on that backend entered through a third proxy. Expiry checks compare the participants, timestamp and request type before removing a stored request.

V4 checks endpoint names, the live player connection, packet fields and the capabilities of the proxy and destination for configurable travel. If placement fails after a backend switch, the player can remain at the new server's join location. Existing named spawns retain their earlier capability negotiation for rolling upgrades. [Wire protocol](../protocol.md) · [Multi-proxy configuration](../multi-proxy.md)

The existing database tables retain ownership, home, warp, route and spawn data. The Bukkit backend obtains its connection and initialises the schema on a database worker. Repository operations wait for the schema and use the pooled circuit breaker. Regional coordinates, radii and safety are resolved on the backend that owns the world. Bukkit-compatible servers use the game thread for synchronous world operations, while Paper uses its native asynchronous operations when available. Bounded request and replay caches protect the network when many requests overlap. [Database](../database.md) · [Redis and TLS](../redis.md)

Fresh installations search the player's world of death for random respawn. An administrator can choose a fixed world or exclude worlds in the active profile. Imported selections and exclusions keep their earlier behaviour. A player who disconnects or dies again cannot be moved by the previous death's pending result.

Packets are limited to 32,766 UTF-8 bytes and 64 payload keys. Player-bound requests must match the carrier and reply endpoints. Redis with TLS checks the certificate against the configured trust store and hostname. Credentials are omitted from diagnostics. The random travel search inspects prepared columns across scheduled tasks, stops at its attempt limit and checks the world's border. [Packet validation](../protocol.md) · [World operations](../platforms.md)

## Upgrade and rollback

1. Stop the instances. Save the current JARs, each plugin data directory and a database backup from the same point in time.
2. Install the matching V4 JARs, restart and check the active profile, migration history, command ownership, old homes and named destinations. Keep local runtime storage with its original backend.
3. Test an ordinary trip, a world-specific route and a named destination as a member. Check a restricted destination as both an authorised and an unauthorised player before enabling additional commands.
4. To roll back, stop all participants and restore the matching previous JARs, complete data directories and database snapshot together. A migration backup contains configuration. It does not contain the database or worlds. [Recovery procedure](../migration.md) · [Historical upgrades](../../LEGACY.md)

### Local build evidence

Maven 3.9.14 completed `clean verify` with 110 common tests, 116 backend tests and seven proxy tests. All 233 ran and passed. The release policy suite passed 36 tests. The command reference check matched 63 declared permissions, eight configurable patterns, 30 command roots and seven aliases. Maven compiled the shared distribution on Java 21 and used JDK 25 for the newer adapter. A repeat build produced identical packaged bytes for each JAR after ZIP metadata normalisation.

On Spigot 1.21.11, an invalid region produced an error naming its field. Checking and reloading an incomplete command configuration left the missing file untouched. With automatic migration disabled, a restart preserved that state. Re-enabling migration and restarting restored the bundled command group.

Three players entered through three separate Velocity proxies. Accepting `/tpa` and `/tpahere` moved the expected player to the other player's world, coordinates and rotation each time. The first player connected to the receiving backend stayed at their original coordinates. MySQL 8.4 also preserved a replacement request when cleanup attempted to delete its predecessor.

The startup layout was checked against all 52 files listed in the backend specification. The JAR supplies 49 editable files. Each backend creates its storage file, migration state and journal and maintains its backup directory. Real Paper, CraftBukkit, Spigot and Purpur 1.21.11 installations matched the packaged guide and all twelve command templates byte for byte. On Paper and CraftBukkit, five successive starts verified stock guide refresh, preservation of administrator notes, restoration of a missing guide, active profile repair and switching to MULTI with an invalid inactive CUSTOM file. The release checks also resolve the guide's relative links from its installed directory.

Every pinned Paper server (15 builds) and all three pinned Velocity proxies passed the two-boot suite. Separate runs passed for the Minecraft 1.21.2 and 26.1 clients, the Velocity 3 and 4 two-client networks and the mixed-generation network with Redis. In the first mixed run, an observer authenticated but its initial game spawn exceeded the fixture’s 45-second deadline under concurrent world generation. The repeat kept every travel assertion, allowed more time for initial client readiness and passed both entry proxies and the older 2.3.0 rollback.

The first 26.1 client fixture expected the older layout with separate dimension directories. The fixture now copies the saved worlds discovered on disk. The final run confirmed an actual 26.1 login on protocol 775 through Velocity 4.3.1 to Paper 26.1.2, and a 1.21.2 login on protocol 768 through Velocity 3.5 to Paper 1.21.3. Both clients reached the named destination at the expected position and rotation.

Published 3.0.1 installations upgraded successfully on MySQL 8.4 and MariaDB 11.4. The tests compared backup contents byte for byte, checked saved homes and aliases, and verified a second V4 boot. In a fresh installation with an unavailable database, the backend wrote the real spawn of a custom-named world and both plugins generated the expected profiles before reporting the failure.

The three-proxy Redis test passed plain delivery and authenticated TLS with a private CA. Each run delivered all 30 timed packets, rejected duplicate processing, retained the current owner after an old proxy reported a disconnect, and resumed after Redis restarted. These timings measure the local bridge, without client loading or world generation.

During the earlier V4 review, a signed-in Minecraft 1.21.11 client joined a separate online-mode Velocity network and used configured spawn commands between Spigot and Purpur. The automated mixed-backend run travelled from CraftBukkit to Spigot to Paper and back. It checked coordinates and rotation on all three arrivals.

Both CraftBukkit and Spigot passed two boots on 17 exact Minecraft releases, from 1.21 through 1.21.11 and from 26.1 through 26.3. The player suite checked named travel, safe random travel, clickable staff commands and the homes inventory on each release through 26.1.2. On 26.2 and 26.3, each distribution passed server lifecycle, database and console command checks. The protocol client used for the suite has no schema for those two releases. Purpur 1.21.11 also passed the player suite.

On standalone CraftBukkit 1.21.11, the protocol client died and respawned on the prepared platform at Y=81, inside an offset world border. The server recorded the selected world and landing coordinates. Regression tests also covered a custom-named world, an unavailable explicit destination and a second death before a pending result could be applied.

A preliminary network run timed out while Multiverse generated a new world with a client connected. The fixture now creates that world before the client joins. It still tests travel into the Multiverse world, permission enforcement, menus, positions and rotations. The distribution workflow also verifies the exact contents of the downloaded build bundle before these tests run.

Spigot 1.21.10 initially completed the protocol handshake but missed its first player spawn deadline as the test server paused when empty. Both a fresh retry and a run with empty-server pausing disabled passed. The platform fixture now allows the same 150-second initial readiness window as the two-proxy clients. Player commands and placement assertions retain their own deadlines.

In a separate checkout, a new dated changelog entry drove a trial 4.0.1 build. The synchronisation command updated all seven POMs and both plugin descriptors. Running it again made no edits. Both trial JARs contained 4.0.1, the release preview selected the stable channel automatically and mismatched tags, versions and channels failed validation.

## Limits

Folia's region-threaded scheduler is outside the supported platform set. A future Minecraft build needs its own boot and travel checks before it can join the verified matrix. A Bukkit API version identifies an interface. A real CraftBukkit, Spigot, Paper or compatible runtime supplies its behaviour. Modrinth uses one entry for the backend JAR across 15 shared Paper, Bukkit and Spigot releases. The exact 1.21.2 and 26.1 CraftBukkit and Spigot builds have separate local coverage. The Velocity entry covers all 17 game versions. Both loader and game-version selections were checked against the public Modrinth catalogue. Refer to the compatibility matrix for exact backend releases. Hosted GitHub Actions and publication to GitHub and Modrinth require a subsequent authorised run.
